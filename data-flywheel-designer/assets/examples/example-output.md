# Data Flywheel — AI code-review suggester

## Feature
- **Model / task:** Fine-tuned instruction LLM that proposes inline review comments on a diff (one comment per file or hunk, with a suggested edit block).
- **User interaction:** Reviewer or author sees the comment in the PR UI and takes one of: **Accept** (apply the suggested edit), **Dismiss** (close without acting), **Edit-then-accept** (modify the suggested edit, then apply), **Ignore** (PR merges without the comment being acted on).

## The 6 Stages

### 1. Cold-start data plan
- **Plan:** Seed dataset of ~5,000 (diff, expert-comment) pairs assembled from three sources: (a) ~2,000 high-quality human review comments mined from the last 12 months of internal PRs where the comment had a linked code change in the same PR (positive examples of "useful comment"); (b) ~2,000 prompted-LLM-as-baseline synthetic examples generated by GPT-class model from diffs sampled across 10 internal repos, then filtered by a senior engineer for accuracy; (c) ~1,000 hand-curated examples written by 3 staff engineers covering categories the mined set under-represents (concurrency, security, perf). v0 model is the prompted baseline; the fine-tune ships at week 6.
- **Why this choice:** Pure synthetic data drifts off-distribution from real diffs; pure mined data over-fits to one team's review style. The 40/40/20 mix gives volume, distribution coverage, and quality anchors. The prompted-LLM baseline lets us launch and start collecting real signal *before* the fine-tune is ready.
- **Failure mode if skipped:** Launching with no v0 means no comments ship, which means no accept/dismiss events, which means there's nothing to fine-tune on at week 6. The flywheel never spins.

### 2. Signal capture
- **Plan:** Log one event per generated comment with these signals — **Explicit:** thumbs-up / thumbs-down button per comment, optional written reason on thumbs-down. **Implicit:** `time_to_action_ms` (dwell), `accepted_without_edit` (boolean), `edit_distance_if_edited` (Levenshtein on the suggested code block), `dismissed_in_under_2s` (almost-certain false-positive signal). **Derived:** `pr_merged_with_comment_addressed` (joined from PR-merge events 24h later), `same_file_re_review_in_7d` (proxy for "the comment missed something important").
- **Why this choice:** Explicit thumbs will be <2% of events; the implicit + derived signals are what carry the flywheel. `edit_distance_if_edited` is the most informative single signal because it captures "directionally right but needed adjustment" — a stronger training signal than binary accept/reject.
- **Failure mode if skipped:** With only thumbs-up/down we'd have <1k labeled events per quarter, statistically useless for fine-tuning. With only `accepted` we'd treat every dismissed comment as a hard negative even when the reviewer just preferred their own phrasing.

### 3. Labeling pipeline
- **Plan:** Three-tier pipeline. **Tier 1 (auto):** events with strong implicit signals are auto-labeled — `accepted_without_edit=true` → positive; `dismissed_in_under_2s=true` → hard negative; ~80% of events flow through this tier at zero marginal cost. **Tier 2 (active-learning queue):** events where the model's own confidence is in the 30–70% band and the user action was ambiguous (edited with high distance, or dwelled >30s and dismissed) go to a human review queue, ~400 events/week. **Tier 3 (gold set):** 50 events/week sampled uniformly are double-labeled by two senior engineers for QC; inter-rater agreement is reported weekly and triggers a labeler-calibration session if it drops below 0.8.
- **Plan (cost):** Tier 2 + 3 = ~450 events/week × ~3 min/label × $1.50/min (internal engineer fully-loaded for a 15-min/day rotation across 6 engineers) ≈ **$2,000/week**. Budget request: $110k/year. Owner: code-review platform team, 6 engineers × 15 min/day on rotation.
- **Why this choice:** 80% auto-labeling keeps cost bounded; active learning routes labeler time to the highest-information samples; the gold set prevents the labeler team from silently drifting (the most common HITL failure mode at month 6).
- **Failure mode if skipped:** "We'll have engineers review some comments" with no rotation, no cost ceiling, and no QC produces a year-1 surprise of either (a) $0 spent and no labels generated, or (b) $40k/quarter spent on labelers who all converged on one reviewer's idiosyncratic style.

### 4. Storage & schema
- **Plan:** One row per generated comment in `code_review_ai_events` Hive table. Schema: `request_id`, `pr_id`, `repo_id`, `file_path_hash` (path is hashed for PII — repo paths can contain usernames), `diff_hunk` (raw, no scrub — code only), `model_version`, `prompt_template_version`, `generated_comment`, `suggested_edit_block`, `user_action` enum, `time_to_action_ms`, `accepted_without_edit`, `edit_distance_if_edited`, `final_edit_block_if_edited`, `derived_signals` (struct, joined nightly), `timestamp`, `reviewer_user_id_hashed`. Retention: 18 months hot, then aggregated stats only. PII: user IDs hashed on write; PR titles / descriptions excluded from the table (only the diff hunk and the model's comment are stored).
- **Why this choice:** 18 months covers four retraining cycles. Hashing user IDs satisfies internal PII review while still allowing per-reviewer model-quality breakdowns. Including `prompt_template_version` separately from `model_version` is the single change that will save us when we want to A/B test prompts inside the same model.
- **Failure mode if skipped:** Without `edit_distance_if_edited` and `final_edit_block_if_edited`, the highest-signal events (edits) become indistinguishable from accepts — at month 6 we'd want to retrain on "what the user *actually* changed it to" and discover we never stored it.

### 5. Retraining trigger
- **Plan:** Fine-tune is triggered when ANY of: (a) **5,000 new Tier-1 + Tier-2 labels accumulate** since the last training run, OR (b) **eval-set acceptance-rate drops 4 percentage points** versus the deployed model on the rolling weekly eval, OR (c) **8 weeks elapsed** since the last training run (anti-staleness floor). Trigger is monitored by a daily cron that opens a JIRA in the code-review platform team's queue and pings the on-call. First retrain expected at ~week 10 post-launch (5k labels at projected ~700/week).
- **Why this choice:** Sample-count threshold catches steady-state growth. Performance-drop threshold catches sudden regressions (e.g., a major language version bump that breaks the model's syntax assumptions). Time floor prevents the model from going stale during low-PR periods (holidays, freezes).
- **Failure mode if skipped:** Without a quantified trigger, retraining happens when someone remembers, which is never. The model's accept-rate decays from 38% at launch to 22% by month 9 and nobody notices until an exec sees a bad comment in their own PR.

### 6. Closing the loop
- **Plan:** Three-stage rollout for every new model version. **(1) Shadow:** new model runs on 100% of traffic but its output is never shown to users; offline scoring compares its comments to the live model's on the same diffs for 1 week. **(2) Canary A/B:** new model serves 5% of PRs across all teams for 1 week; guardrail metric is `accepted_without_edit` rate — auto-rollback if it drops more than 3pp vs control with p<0.05. **(3) Ramp:** 5% → 25% → 100% over the following 2 weeks if guardrail stays green. **Holdout:** 1% of PRs permanently see the v0 prompted baseline so we can measure long-term cumulative improvement of the flywheel. Rollback owner: code-review platform on-call (paged by the auto-rollback alert).
- **Why this choice:** Shadow gives offline confidence cheaply; A/B gives causal evidence; the ramp limits blast radius; the 1% permanent holdout is the only way to answer "is the flywheel actually working over months" without confounding from prompt and infra changes.
- **Failure mode if skipped:** A "better on eval" model gets pushed to 100% on Friday, silently degrades on a language the eval underweighted, and the team spends Monday morning debating whether to revert instead of having a one-click rollback already armed.

## What to build first
- **Before launch (week 0):** cold-start dataset (Stage 1) + storage schema with `edit_distance_if_edited` field already present (Stage 4) + at least the implicit signals already wired into the logger (Stage 2). Without these three, nothing else matters.
- **Launch through week 4:** Tier-1 auto-labeling (Stage 3) and the shadow-deploy harness (Stage 6) — both are cheap and unblock the first retraining cycle.
- **Weeks 4–10:** Tier-2 active-learning queue (Stage 3) and the retraining trigger cron (Stage 5).
- **Blocking dependency:** the storage schema. Every other stage either consumes its rows or assumes a specific field exists. If schema slips, the entire flywheel slips with it.

## Open questions
- Do we have legal sign-off to mine historical PR comments for the cold-start set, or do we need engineer opt-in?
- Who pays for the labeler-engineer rotation — the AI team's headcount, or the platform team's?
- What's the right eval set? "Held-out PRs from the cold-start mined set" risks evaluating only on the source distribution; we likely need a fresh weekly eval sampled from live traffic, but that requires resolving the labeling-of-eval question separately.
