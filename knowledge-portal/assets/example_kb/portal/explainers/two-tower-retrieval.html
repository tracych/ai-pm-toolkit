Two-tower retrieval

systems_and_models · last updated 2026-05-12

What it is

A neural retrieval model that learns one embedding for the user and one embedding for the item, then ranks items by similarity to the user embedding.

Why it matters

The current candidate generator (v1) uses a co-visitation graph — items get linked when users view them in the same session. It's robust but it has two ceilings: it can't generalize to items with sparse history, and it can't use rich user features (tenure, category preference history, session signal).

Two-tower lifts both ceilings. It learns from the same view/purchase data v1 uses, but represents both sides as dense vectors, so items with thin history still get reasonable scores via similarity to similar items, and users get scored via similarity to similar users.

How it works

  • Two neural networks ("towers") share no parameters. One takes user features; the other takes item features.
  • Each tower outputs a fixed-dimensional embedding (we use 128).
  • Similarity = dot product. Training objective: in-batch sampled softmax — push the positive item's score up vs random negatives.
  • At serving: precompute item embeddings for the entire catalog (offline, daily). At request time, run only the user tower (~ms) and find top-K nearest items via ANN.
  • ANN backend: HNSW with M=32, ef_search=64. Tradeoff knob: ef_search up = recall up, latency up.

Where it lives

  • Training: services/recs/two_tower/train.py
  • Serving (user tower): services/recs/two_tower/serving/
  • ANN index build: nightly job recs-two-tower-ann-index
  • Eval harness: services/recs/eval/harness.py (NDCG@10 cut by user tenure)

Key tradeoffs

TradeoffOur choiceWhy
Embedding dim128256 was +0.4% NDCG, +30% serving latency — not worth it
Negative samplingIn-batch + uniform randomIn-batch alone overfits to popular items
User tower inputLast 50 actions + tenure bucket + category prefsLonger history was costly to fetch at serve time; 50 captures most signal
Item tower refreshDailyItem embeddings drift slowly; daily is fine, hourly would waste compute

What you should NOT do

  • Don't compare scores across training runs. Scores are not calibrated; only ranks within a run are meaningful.
  • Don't bypass the ANN. Brute-force scoring against 12M items at request time will blow latency.
  • Don't infer cold-start performance from global NDCG. Always look at the by-tenure cut.
  • Don't add user features without consulting modeling. Every feature in the user tower adds serve-time fetch cost. Audit before adding.
