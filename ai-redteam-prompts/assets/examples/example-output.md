# AI Red-Team Prompts — customer-email-agent

## Feature

> An AI agent that reads incoming customer emails and can draft and send replies after a human approves.

## Blast radius assumptions

- **Input source:** Untrusted. Inbound email body is fully attacker-controlled (any sender on the public internet).
- **Output consumer:** A human reviewer who reads the drafted reply, clicks Approve, and sends. Approver is a support agent on a queue, optimizing for speed — likely to skim under load.
- **Tools available to the agent:** `draft_reply(to, subject, body)`, `send_reply(draft_id)` (gated by human approval), `lookup_order(email)`, `lookup_account(email)`. Account lookup returns PII (name, address, last-4-card, order history).
- **Retrieved content in input:** Yes — the agent retrieves prior conversation history and the customer's account record into context. Both routes carry injection risk.
- **Multi-turn:** Effectively single-turn per email, but a thread can contain many emails, so jailbreak persistence across thread history is in scope.
- **Worst plausible outcome:** Agent drafts a reply that (a) exfiltrates another customer's PII, (b) sends a reply that defames / harasses the customer and the approver waves it through, or (c) takes a hostile action via the account-lookup tool to pull a record the attacker is not entitled to.

## Top 5 fix-before-launch

1. **Direct-injection system-prompt leak (row 3, priority 25).** Mitigation: add an output filter that scans drafts for known system-prompt n-grams and blocks send when matched. Owner question: who on the platform / safety team owns the output-filter regression suite?
2. **Indirect-injection cross-customer PII exfiltration via planted system note in inbound email (row 1, priority 20).** Mitigation: bind `lookup_account` arguments to the verified sender's email address; reject any tool call whose argument differs. Owner question: who on the agent-tools team will land and test the binding before launch?
3. **Cross-account lookup induced by social-engineering text (row 2, priority 20).** Mitigation: same binding as row 1 — agent may only look up the verified sender; cross-account flows require a separate authenticated journey. Owner question: same as row 2; confirm one fix closes both rows.
4. **Hidden-HTML indirect injection causing mass-PII pull across thread participants (row 15, priority 10 — included in top-5 because it shares the cross-account harm class with rows 1 & 2 and the fix is adjacent).** Mitigation: strip HTML comments and zero-contrast text from inbound content before model context; rate-limit `lookup_account` per inbound message. Owner question: who owns inbound-email sanitization?
5. **Jailbreak / role-play producing off-brand or abusive drafts that a tired approver waves through (rows 6, 14, 18 — combined; priorities 16/12/16).** Mitigation: brand-voice + toxicity classifier on outbound drafts (post-any-transform); drafts flagged off-tone require a secondary approval. Owner question: which model owns the brand-voice classifier, and what's its current FPR / FNR on the approver queue?

## What this red-team CANNOT cover

- These are *single-turn prompts*. Multi-turn jailbreak drift across a long email thread, where each message nudges the agent further, is not covered. Refresh with multi-turn scenarios before launch.
- This is *prompt-level* red-teaming. Tool-integration failures (the agent calls the right tool with wrong arguments, the tool itself has a bug, the approval-token verification has a race condition) are not covered — that's a tool / infra audit.
- This is *static at generation time*. New jailbreak techniques emerge weekly; refresh this set before each major launch and quarterly after.
- This *predicts* failures based on category patterns. Only running the prompts against the live agent + tools, in a staging environment with real retrieval and real tool responses, tells you which ones actually land.
- Bias probes here are *spot checks*. A real fairness audit needs a representative name / domain / language suite and statistical analysis of disposition rates across groups — not 2 pairs.
- This does not cover **non-prompt** attack surfaces: account-takeover via auth flows, social engineering of the human approver outside the email channel, supply-chain compromise of the model or tool code, or exfiltration via logs and traces.
